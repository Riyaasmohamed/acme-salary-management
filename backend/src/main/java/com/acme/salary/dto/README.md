# `dto` — the JSON contract of the API

DTOs (Data Transfer Objects) are the shapes of the JSON that goes in and out of the API.
They are Java **records**: immutable, with constructor, accessors, `equals` and `toString`
generated by the compiler.

| Class | Direction | Purpose |
|---|---|---|
| `EmployeeRequest` | in | Body of create/update. Carries the **validation rules** (`@NotBlank`, `@Email`, `@Positive`, `@PastOrPresent`, `@ValidCurrency`, size limits). |
| `EmployeeResponse` | out | An employee including `id`, `createdAt`, `updatedAt`. |
| `PageResponse<T>` | out | One page: `content`, `page`, `size`, `totalElements`, `totalPages`. Replaces Spring's `Page`, whose JSON is not a stable contract. |
| `EmployeeSortField` | in | The only columns the list can be sorted by (`NAME`, `SALARY`, `HIRE_DATE`). Adds `id` as a tie-breaker so paging is stable. |
| `FilterOptions` | out | Distinct countries, job titles and departments for the dropdowns. |
| `CountrySalaryStats` | out | min / max / average / count for one country and currency. |
| `JobTitleSalaryStats` | out | the same for one job title within a country. |
| `CountryHeadcount` | out | number of employees in one country. |

**Why DTOs instead of returning the entity:**

- The API does not change when the table changes.
- Clients cannot set fields they must not control (`id`, timestamps).
- Validation belongs to "what a request may contain", not to the database mapping.
- No risk of accidentally serialising lazy-loaded relations or internal fields.
